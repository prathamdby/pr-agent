# Context glossary

This file is **domain language only** — not a specification of how the system is implemented.

- **Webhook delivery** — A single signed HTTP POST from GitHub to your app, identified by the `X-GitHub-Delivery` header (or deduplicated by raw body hash when that header is missing). Under the durable-queue design, every accepted delivery is recorded in durable storage before the HTTP response; duplicate deliveries are rejected by that record, not an in-memory map. A burst of deliveries must not be dropped at intake because workers are busy.
- **PR conversation** — The main pull request discussion timeline (GitHub models this as comments on an issue).
- **Inline review thread** — A thread anchored to a specific line/diff review comment on a pull request.
- **PR-surface I/O** — The set of GitHub REST calls the app makes around a pull request: acknowledgement reactions; creating or updating the review progress comment; posting or editing ask answers on the PR conversation or an inline review thread; fetching the PR head SHA; and publish-time review mutations (inline review threads, labels).
- **Slash command** — A **new** (`created`) comment whose first non-empty line begins with `/` followed by a command token.
- **Command issuer** — Anyone who can participate in the PR comment surface where the command appears.
- **Reply target** — Descriptor for where a slash command's response should appear (PR conversation vs inline review thread).
- **Draft pull request** — A PR still marked draft; this service runs the same automation on draft PRs as on ready PRs.
- **Acknowledgement reaction** — GitHub `eyes` / 👀 signaling that a webhook was accepted and work is in progress (on the PR issue and/or triggering comment). For automated pull request reviews, scheduled at durable webhook intake and published by a high-priority acknowledgement worker together with the review progress comment stub, before the review run starts.
- **Agent work item** — A durable unit of background work created from a webhook delivery or slash command: a review, an ask, a description, or a triage run. Tracks lifecycle (queued, running, superseded, cancelled, completed, failed) independently of the HTTP request that created it.
- **Description run** — Execution of an agent work item that generates a concise PR description (type, summary bullets, optional Mermaid diagram, file walkthrough) and publishes by merging into the pull request body. Triggered automatically on `pull_request` `opened` events and by `/describe`.
- **Description queue** — pg-boss `agent-work-description` lane with worker concurrency `DESCRIPTION_CONCURRENCY` (default `1`) and per-PR `key_strict_fifo` singleton keys.
- **Description agent block** — Generated markdown under `## PR Agent Description` in the PR body. Re-runs replace only this block; content above the header is treated as user-authored.
- **Triage run** — Slash-triggered work item for `/triage` that verifies prior PR Agent inline findings, fixes valid same-repo findings in a writable checkout, commits one fix per finding, pushes, then reports verdicts. Historical findings published by the removed review-lens commands remain eligible. PR-conversation `/triage` scopes to all eligible findings; inline-thread `/triage` scopes to one finding.
- **Triage verdict** — Per-finding outcome: `fixed`, `already-resolved`, `skipped`, or `dismissed`. Dismissed findings require maintainer reply evidence and are never auto-resolved. Shared vocabulary between **Triage run** and **Verification run**.
- **Verification run** — Automated, read-only agent work item triggered when new commits land on a pull request that has open PR Agent findings. It re-checks each prior finding against the new head and emits a **triage verdict** per finding. Publish is quiet by default: **fixed** and **already-resolved** findings are resolved on the **inline review thread** with no reply; only **skipped** (still open, and only when that finding's file changed in the push) and **dismissed** findings get a thread reply (dismissed also offers a **policy suggestion**). It never opens new findings, never edits code, and never uses a **writable PR checkout**. Skipped when the PR has no open findings; rapid pushes collapse to the newest head under the same superseding rules as automated reviews. Distinct from a **Review run** (which finds new issues) and a **Triage run** (which fixes them).
- **Triage report comment** — PR conversation comment under `## PR Agent Triage` with evaluated head SHA, pushed commits, verdict counts, and a per-finding table.
- **Writable PR checkout** — Fresh full clone for one triage run. It is never the shared PR repository view cache, never force-pushed, and only pushes fast-forward commits to the PR head branch.
- **Local PR workspace** — A temporary shallow checkout of the pull request head plus server-owned PR diff metadata, used by a **Review run**, **Ask run**, or **Description run** so the agent can inspect the full repository tree at the PR head without using GitHub read tools as its investigation surface.
- **PR repository view cache** — Worker-process ref-counted cache keyed by `owner/repo#pr:headSha` so concurrent jobs for the same PR commit share one git clone; released when the last job finishes.
- **Review run** — Execution of one durable review work item scoped to a pull request, triggered by configured automated `pull_request` events or `/review`. It builds a shared **Review evidence snapshot**, fans out to **Reviewer critics**, validates high-risk candidates, performs **Review synthesis**, and publishes at most one **Review payload**. Removed review-lens commands do not create review runs.
- **Reviewer agent** — One independent, read-only agent session assigned a review angle: correctness, security, tests, maintainability, project standards, reliability, API/contracts, or adversarial analysis. Used by the legacy **Review pipeline mode**. A **Review run** selects which Reviewer agents to run from the **Review budget tier**. Reviewer agents cannot publish and finish by submitting one internal **Reviewer report**.
- **Reviewer critic** — One of four independent, read-only agent sessions in the hybrid **Review pipeline mode**, each assigned a risk domain: correctness, security, reliability, or change-safety. Every full hybrid Review runs all four critics in one parallel wave regardless of **Review budget tier**. Critics start from the shared **Review evidence snapshot** and may use bounded follow-up reads, searches, and diffs. Critics cannot publish and finish by submitting one internal **Reviewer report**.
- **Review evidence snapshot** — Immutable, versioned, server-owned packet covering every changed path, bounded diff context, applicable repository contracts, prior inline feedback, and explicit coverage gaps. Identified by a deterministic evidence hash so every critic, validator, and synthesis call can prove it reasoned over the same PR state.
- **Review pipeline mode** — Rollout selector for the Review pipeline: `legacy` (eight-role **Reviewer agent** roster), `shadow` (legacy publishes plus a sampled non-publishing hybrid comparison), or `hybrid` (four **Reviewer critic** pipeline publishes). Default is `legacy` until replay, shadow, and canary gates pass.
- **Review orchestrator** — The only agent session in a **Review run** that receives `submitReview`. It synthesizes the reviewer reports, resolves conflicts with read-only tools, removes unsupported or duplicate claims, and owns the single final publish attempt sequence. It does not rediscover the full change set. In hybrid mode the synthesis session is submission-only with no investigation tools.
- **Reviewer report** — Internal structured output from a **Reviewer agent** or **Reviewer critic**: coverage, evidenced candidate findings, residual risks, and testing gaps. It is input to validation and synthesis, not a GitHub-visible review.
- **Review synthesis** — The fan-in stage where the **Review orchestrator** combines validated reviewer reports into the single public **Review payload**. Completion order of parallel reviewer agents or critics does not define publication order. In hybrid mode, synthesis is one submission-only model turn with no investigation tools.
- **Degraded review** — A review synthesis performed without one or more selected non-required reviewer reports. Correctness, security, and reliability are required coverage in hybrid mode; if any is unavailable, the Review run fails instead of publishing a degraded review. Change-safety failure after its isolated retry permits an explicitly degraded Review. Reviewer agents omitted by **Review budget tier** policy are not degradation.
- **Review budget tier** — Classification of pull request size (`small`, `medium`, or `large`) used to steer investigation focus and SLO exemption. In legacy mode it also selects the Reviewer-agent roster. In hybrid mode all tiers run the same four critics. Does not by itself cancel a **Review run**.
- **Agent session** — One provider-side conversation inside an agent work item execution. A **Review run** owns multiple isolated reviewer and validator sessions plus one orchestrator session; provider state is not reused across those sessions or across jobs.
- **Review phase** — Named stage within the orchestrator publish loop, used for metrics and retry attribution after reviewer fan-out: **investigation** (synthesis and targeted checks before submit), **pre_submit** (nudge to call submitReview), **validation_repair** (fix ReviewPayload after schema/anchor errors), **publish_recovery** (retry after publish did not succeed), **plaintext_fallback** (maintainer failure notice when structured publish is exhausted).
- **Review queue** — pg-boss `agent-work-review` lane for review runs, with worker concurrency `REVIEW_CONCURRENCY` (default `2`) and one per-PR `key_strict_fifo` singleton key. Each active Review run may execute up to `REVIEW_AGENT_CONCURRENCY` (default `4`, env-backed) reviewer sessions at once. Work is persisted in `agent_work_items` before the webhook returns; not strict FIFO across all pull requests.
- **Review superseding** — When a newer automated review is scheduled for the same pull request, older queued auto-review work for that PR is abandoned in favor of the latest head SHA. An in-flight auto-review may be cooperatively cancelled and replaced by one follow-up run for the newest head. Applies to automated `pull_request` events only, not slash-command reviews. A cancelled auto-review must not publish partial review output. The review progress comment may be edited once to note supersession before the newer run’s intake replaces it with a fresh in-progress stub.
- **Slash review deduplication** — If a command issuer invokes `/review` while a Review run is already queued or in progress for that pull request, the bot acknowledges with a short reply on the command thread but does not enqueue duplicate work or alter the existing review progress comment.
- **Review stale-head reschedule** — If a slash-command or automated review reaches publish (or aborts mid-flight) after the pull request head has changed, the bot may schedule one replacement run for the latest head while preserving the original source and command context. If that replacement also goes stale, the run fails with retry guidance instead of rescheduling indefinitely. Distinct from **Review superseding**: intake-driven supersede still applies only to automated `pull_request` events and does not cancel slash-command reviews.
- **Webhook parse error** — The JSON failed validation at the app boundary (unexpected or missing fields for that event type); the delivery is not treated as processed for deduplication until parsing succeeds.
- **Review payload** — The structured, validated description of a completed review run (findings plus overview gates), emitted once per review run via `submitReview`.
- **Review progress comment** — The single PR conversation comment identified by `## PR Agent Review`. Published as a short in-progress stub by the acknowledgement worker after durable intake, then edited in place with the final review summary when the Review run completes. Re-runs update the same comment rather than posting a new one.
- **Review pointer body** — The top-level body of a pull request review on the Files Changed tab; points readers to the review summary comment and may host the agent fix prompt accordion.
- **Review pointer link** — On later Review runs, the review pointer body is only a markdown link to the existing review summary comment (`View the updated review`). Omitted on the first completed-summary publish for that pull request.
- **Agent fix prompt** — Aggregate, copy-pasteable fix instructions for coding agents, combining all findings from a review run.
- **Finding fix prompt** — Per-finding copy-paste instructions inside an inline review thread’s “Prompt to fix” accordion; server-rendered (shared preamble and PR metadata, location header, then model-authored bug and fix direction). Distinct from the agent fix prompt aggregate on the review pointer body.
- **Suggestion patch** — Optional GitHub-native ` ```suggestion ` block attached to a finding’s inline review thread, offering a one-click applyable fix for human reviewers. Present only when the fix is mechanically expressible within the finding’s **commentable right line range**; findings needing cross-file or conceptual fixes carry only the **finding fix prompt**. Secondary to the fix prompts: the product is agent-first, human-visible second.
- **Review summary comment** — The completed form of a review progress comment: navigation and overview gates, not duplicated finding bodies from inline review threads. Owns "what's risky" (merge verdict, gates, findings table); never carries a per-file walkthrough. When a description agent block exists on the PR, the summary links to its file walkthrough instead of duplicating it.
- **Finding confidence** — Per-finding certainty level (`c2`–`c4`) shown beside severity in the review summary comment; expresses how sure the reviewer is about one finding, nothing else.
- **Merge verdict** — Model-authored readiness assessment in the review summary comment: a score plus a one-sentence rationale written about the run's own findings. Consistency-clamped: open P1 findings cap the score and forbid safe-to-merge wording, enforced by review payload validation. All verdict and security wording is pass-scoped ("on this pass"), never an absolute safety promise. Distinct from **finding confidence**.
- **Prose contract** — Changed Markdown that defines behavior (agent instructions, skill definitions, configuration docs) rather than merely describing it. The project-standards reviewer checks prose contracts for internal consistency: counts vs listed items, cross-references that resolve, command examples that are neither broken nor destructive, stated defaults vs the rest of the diff. Contradictions are ordinary findings, not style nits.
- **Probable secondary rate limit** — GitHub returned an auth-shaped error while the installation token is still within its TTL; treated as a likely pacing/abuse limit for logging and cooldown, not a confirmed diagnosis.
- **Truncated change set** — File listing for a review run where some changed files are omitted due to configured caps; the run continues with explicit truncation metadata.
- **Ask run** — Execution of an agent work item that answers a command issuer's question about PR code; triggered by `/ask` only; produces a plain-text **ask answer** (not a review payload or review summary comment). Each ask run is independent; prior ask runs or thread comments are not used as context.
- **Ask queue** — pg-boss `agent-work-ask` lane for ask runs, with worker concurrency `ASK_CONCURRENCY` (default `1`). Isolated from the review queue so review backlog cannot starve interactive Q&A.
- **Code anchor** — File path, line range, and diff hunk from an inline review comment; tells an ask run which code the command issuer was looking at.
- **Review failure notice** — A short PR conversation comment posted when a review run reaches a terminal failed state after retries, telling maintainers the review did not complete and how to retry (for example `/review`). Uses neutral user-facing wording only; no attempt counts, tooling failures, or internal reasoning. Usually delivered by editing the existing review progress comment in place.
- **Summary-only finding** — A validated review finding that appears in the PR conversation summary because no stable inline review thread anchor exists on the cached PR diff. Not a failed review.
- **Commentable right line range** — A contiguous line range on the PR head (`RIGHT`) side that GitHub accepts for inline review comments, derived from the cached unified diff captured during `listPullRequestFiles`.
- **Public-output sanitizer** — Server-side guard that replaces credential- and assignment-shaped substrings in PR-visible **review** text before posting (substring `[redacted]`, not whole-field replacement). Overview internal failure phrasing is blocked separately by **Review payload** validation (reject → repair loop), not by the sanitizer.
- **Unslop writing** — Shared prompt contract for PR-visible model output (ask answers, review fields, descriptions, triage/verification evidence): cut AI tells, prefer concrete plain speech, and keep a human voice. Inlined from `src/agent/prompts/unslopGuidance.ts`; enforcement is prompt-only plus matching server-rendered copy.
- **Publish execution budget** — The maximum number of valid `submitReview` publish executions allowed per review run (`MAX_REVIEW_PUBLISH_CALLS`, default 2). Validation-only retries do not count.
- **Ask failure reply** — Plain-text failure message posted at the ask reply target when an ask run fails permanently after retries.
- **Ask meta refusal** — A short ask answer posted without an LLM run when the question targets bot configuration, credentials, or internal instructions; distinct from an Ask run that investigates PR code.
- **Lightweight review completion** — An automated review work item that finishes without a **Review run** because the change set qualified for a **Trivial change exemption**. Acknowledgement reaction and review progress comment intake still occur; the review progress comment is updated in place with a short public notice instead of a full review summary produced from a **Review payload**.
- **Trivial change exemption** — Policy allowing **Lightweight review completion** on automated pull request reviews when every changed file matches the docs-only allowlist and the change set is not a **Truncated change set**. Slash-command reviews are not exempted.
- **Finding fingerprint** — Stable identifier for a published finding, derived server-side from finding location and substance, used to recognize the same issue across unified Review runs on one pull request. Historical lens-specific fingerprints remain stored with their original publish records.
- **Stale review metadata** — Hidden machine-readable HTML comment in the **review summary comment** recording head SHA, review identity, and whether the reviewed head was stale when published. New reviews always use the `review` identity.
- **Dropped inline anchor note** — Capped maintainer note on the **review pointer body** listing inline comments skipped because GitHub rejected their diff anchors; affected findings remain in the **review summary comment**.
- **Prior inline review feedback** — Trusted context from earlier unified bot **inline review threads** on the same pull request where a maintainer replied; the Review run must weigh dismissals (for example false positive) before re-reporting.
- **Repo policy file** — Maintainer-authored, version-controlled configuration in the repository (path patterns plus instructions) that durably steers review behavior. The only cross-PR preference memory: the bot never learns silently from thread replies.
- **Policy suggestion** — Bot-drafted repo policy file line offered when a maintainer dismisses a finding, so the maintainer can commit the preference explicitly. The bot proposes the memory; a human review commits it.
- **Fingerprint suppression** — Skipping a new **inline review thread** when its **finding fingerprint** matches one already recorded for the same pull request and unified review identity; the issue may still appear in the **review summary comment**.
