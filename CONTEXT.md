# Context glossary

This file is **domain language only** — not a specification of how the system is implemented.

- **Webhook delivery** — A single signed HTTP POST from GitHub to your app, identified by the `X-GitHub-Delivery` header (or deduplicated by raw body hash when that header is missing). Under the durable-queue design, every accepted delivery is recorded in durable storage before the HTTP response; duplicate deliveries are rejected by that record, not an in-memory map. A burst of deliveries must not be dropped at intake because workers are busy.
- **PR conversation** — The main pull request discussion timeline (GitHub models this as comments on an issue).
- **Inline review thread** — A thread anchored to a specific line/diff review comment on a pull request.
- **PR-surface I/O** — The set of GitHub REST calls the app makes around a pull request: acknowledgement reactions; creating or updating the review progress comment; posting or editing ask answers on the PR conversation or an inline review thread; fetching the PR head SHA and lifecycle state; and publish-time review mutations (inline review threads, labels, checks, statuses, and the PR body). Worker and feature code reach this surface only through the **PR surface seam** (`createPrSurface` / `PrSurface` in `src/github/prSurface.ts`); leased workers inject the epoch-aware, cancellation-aware mutation boundary, while read-only calls remain available for recovery. Raw Octokit construction and installation-token parameters stay inside `src/github/`.
- **Slash command** — A **new** (`created`) comment whose first non-empty line begins with `/` followed by a command token.
- **Command issuer** — Anyone who can participate in the PR comment surface where the command appears.
- **Commenter** — A GitHub comment author represented by server-preserved user id and `author_association` metadata. Comment text, display names, and the ability to reply are not authorization signals.
- **Authorized maintainer decision** — A non-bot reply from a known GitHub user whose server-preserved association is included in `MAINTAINER_DECISION_ASSOCIATIONS`; it is decision evidence only for the matching finding thread. Reply bodies remain untrusted input.
- **Reply target** — Descriptor for where a slash command's response should appear (PR conversation vs inline review thread).
- **Draft pull request** — A PR still marked draft; this service runs the same automation on draft PRs as on ready PRs.
- **Acknowledgement reaction** — GitHub reaction lifecycle on the PR issue and/or triggering comment: `eyes` / 👀 when work is accepted (in progress), `+1` / 👍 when it completes successfully (including when findings were published), and `-1` / 👎 when it fails terminally. Exactly one of these lifecycle reactions is kept at a time: each transition replaces the bot's prior `eyes`/`+1`/`-1` on that target. For automated pull request reviews, the eyes reaction is scheduled at durable webhook intake and published by a high-priority acknowledgement worker together with the review progress comment stub, before the orchestrated review run starts. Completion and failure reactions are published by the durable work runner after terminal status transitions.
- **Agent work item** — A durable unit of background work created from a webhook delivery or slash command: a review, an ask, a description, a triage run, or a verification run. Tracks lifecycle (queued, running, superseded, cancelled, completed, failed) independently of the HTTP request that created it.
- **PR actor lease** — The single source of truth for "one active run per PR per work type": a `pr_actor_leases` row keyed by (resource key, work type) with a monotonic **lease epoch**. Review, description, triage, and verification workers acquire the lease before claiming the work item, renew it while running, and release it on completion; every durable state write and every leased PR-surface mutation is fenced on the epoch, with operation intents and publish records retaining the epoch for reconciliation. Renewal loss aborts the mutation signal and blocks stale completion. A delivery that finds the lease held completes as a no-op, arming one throttled redelivery that re-checks every defer interval — this is both the queued-behind path (`/review force`, stale-head replacement) and the crash-recovery watchdog (a dead holder's lease is stolen once its TTL lapses). Ask work items are unleased and rely on publish-record idempotency.

- **Description run** — Execution of an agent work item that generates a PR description (type, summary bullets sized by **body scale**, optional Mermaid diagram, optional **review map**) and publishes by merging into the pull request body. Triggered automatically on `pull_request` `opened` events and by `/describe`. Description prose follows ASD-STE100 (short active sentences, one idea per word, one topic per bullet).
- **Description writing policy** — Single size→behaviour decision for a description run. Derived once from workspace `fileCount`, `totalChanges`, and truncation. Owns **body scale**, **map mode**, bullet range, max words per bullet, and technical depth. Injected as hard prompt rules in the description user message.
- **Body scale** — `brief`, `standard`, or `detailed` for description bullet count and depth. **brief** on short PRs (at most 5 files, under 300 line changes, not truncated); **standard** up to 20 files and under 1500 line changes; **detailed** otherwise or when truncated. Each scale sets bullet min/max, words per bullet, and technical depth (`what_why` | `what_why_risk` | `what_why_how`).
- **Review map** — Always-visible ordered list (at most five files) in the description agent block telling reviewers which paths to open first and why. Server chooses **map mode** from the writing policy: **omit** on short PRs (same thresholds as brief body scale) so no map section is published; **read-first** otherwise. Not a nested file walkthrough and not grouped by PR-type labels.
- **Map mode** — `omit` or `read_first` for a description run. Part of the writing policy; injected as a hard prompt rule and enforced on `submitDescription` (strip on omit, cap at five on read-first).
- **Description queue** — pg-boss `agent-work-description` lane with worker concurrency `DESCRIPTION_CONCURRENCY` (default `1`); per-PR mutual exclusion comes from the **PR actor lease**, not the queue.
- **Description agent block** — Generated markdown under `## PR Agent Description`, wrapped in `<!-- PR_AGENT_DESCRIPTION_BEGIN -->` / `<!-- PR_AGENT_DESCRIPTION_END -->` markers in the PR body. Re-runs replace only this marked region; content outside the markers is treated as user-authored.
- **Triage run** — Slash-triggered work item for `/triage` that verifies prior PR Agent inline findings (P0–P3) from the current specialist run and recognized legacy lens threads, fixes valid same-repo findings in a writable checkout, commits one fix per finding, pushes, then reports verdicts. PR-conversation `/triage` scopes to all eligible findings; inline-thread `/triage` scopes to one finding. Each fix commit attributes **author and committer** to the human **command issuer** who posted `/triage` (GitHub profile name + public email, or id-based `users.noreply.github.com` when email is private) and adds a `Co-authored-by` trailer for the GitHub App. When the issuer is the App/bot or identity cannot be resolved, author and committer stay the App and the App co-author trailer is omitted. Close/merge cancellation makes queued work terminal and stops running work at a checkpoint; current PR state is checked through the PR surface immediately before commit and push, and closed/merged PRs receive a no-push terminal outcome.
- **Triage verdict** — Per-finding outcome: `fixed`, `already-resolved`, `skipped`, or `dismissed`. Dismissed findings require an authorized maintainer decision matching the finding thread; all other replies are untrusted evidence. **Triage run** resolves the **inline review thread** when the verdict is `fixed` (after a successful push), `already-resolved`, or `dismissed`. `skipped` stays open. **Verification run** acknowledges dismiss on its **verification stub** then resolves the thread. Shared vocabulary between **Triage run** and **Verification run**.
- **Verification run** — Read-only agent work item enqueued on `pull_request` `synchronize` when `FEATURE_VERIFICATION=auto`, or on `/verify` when the feature is not `off`. It re-checks each prior finding against the new head and emits a **triage verdict** per finding. Publish is quiet by default: **fixed** and **already-resolved** findings are resolved on the **inline review thread** with no new reply (if a prior **verification stub** exists, it is edited in place to a short fixed/already-resolved line so a stale still-open signal is not left behind); **skipped** (still open, and only when that finding's file changed in the push) updates one verification stub in place; **dismissed** edits that stub (evidence + **policy suggestion**) then resolves the thread. It never opens new findings, never edits code, and never uses a **writable PR checkout**. The worker short-circuits without an agent run when the PR has no unresolved open findings; rapid pushes collapse to the newest head under the same superseding rules as automated reviews. Immediately before publish, the executor compares the bound head SHA to the live head. Inequality skips publish, logs both SHAs on the existing skip line, and completes degraded (`publishDegraded`) so a clean completed run still means that head was checked. Slash `/verify` has no replacement run; auto `synchronize` already enqueued one. Distinct from an **Orchestrated review run** (which finds new issues) and a **Triage run** (which fixes them).
- **Verification stub** — The single bot reply on an **inline review thread** owned by **Verification run**, marked with `<!-- pr-agent:verification-stub -->`. Later verification publishes edit this comment instead of stacking new replies.
- **Triage report comment** — PR conversation comment under `## PR Agent Triage` with evaluated head SHA, pushed commits, verdict counts, and a per-finding table.
- **Writable PR checkout** — Fresh full clone for one triage run. It is never the shared PR repository view cache, never force-pushed, and only pushes fast-forward commits to the PR head branch. Final lifecycle guards through `PrSurface` run immediately before commit and push, so closed or merged PRs cannot receive new triage writes. Per-commit git identity uses `GIT_AUTHOR_*` / `GIT_COMMITTER_*` for the triage triggerer (or App fallback) without rewriting global `user.*` mid-run; human-attributed commits carry an App `Co-authored-by` trailer.
- **Local PR workspace** — A temporary shallow checkout of the pull request head plus server-owned PR diff metadata, used by an **Orchestrated review run**, **Ask run**, **Description run**, or **Verification run** so the agent can inspect the full repository tree at the PR head without using GitHub read tools as its investigation surface.
- **PR repository view cache** — Worker-process ref-counted cache keyed by `owner/repo#pr:headSha` so concurrent jobs for the same PR commit share one git clone; released when the last job finishes. Uncached preparation uses the canonical capped GitHub changed-file list; a truncated or incomplete caller-supplied list cannot determine the cached view.
- **Orchestrated review run**. The single review work item for a pull request. It performs reconnaissance, authors a specialist brief, runs four specialists, publishes incremental thread batches, and writes the final summary. PR metadata, reconnaissance output, briefs, workspace results, and external-tool results reach model sessions as untrusted evidence.
- **Review orchestrator**. The long-lived agent session that inspects the pull request, authors the specialist brief, judges reports, publishes thread batches, and synthesizes the summary. Its system instructions, reporting contracts, severity rules, and publish gates remain server-owned. During judgment it independently re-applies the **causal-publication contract**; specialist reports cannot publish directly.
- **Specialist**. One of four fixed investigator sessions: correctness, security, quality, or tests. Specialists run in parallel with a persona prompt and the specialist brief. Embedded evidence cannot suppress, omit, downgrade, or relabel an evidenced finding. Quality owns structural defects only when the structure already causes present harm. Tests owns a missing check only when it names the changed behaviour, untested state, invariant, and plausible regression.
- **Specialist brief**. The structured handoff containing pull request intent, architecture notes, risk areas, a file map, and focus for each specialist. Those fields carry the **risk map**. Every field is untrusted evidence, even when the server validates its shape.
- **Risk map**. Bounded reconnaissance hypotheses in the specialist brief. It names applicable contract-edge, boundary, lifecycle, and state-symmetry risks when the change set suggests them. It prioritizes specialist attention. It cannot publish, suppress, or assign severity.
- **Specialist report**. One specialist's structured submission. The server validates its schema, workspace evidence, checkout coverage, and publish gates; report text remains evidence. `no_findings` is an explicit successful empty report, not an error. A report is never authority over publication.
- **Causal-publication contract**. Shared rule for a publishable review finding: one atomic problem with a concrete trigger, PR-introduced or PR-exposed wrong behaviour or a precise unprotected regression, an observable consequence, reviewed-head evidence the evidence ledger can authorize, and a bounded fix direction. Specialist-specific floors stay on top of this shared floor. Independently fixable root causes stay separate findings. P3 remains available for a real low-impact defect that meets the contract. Silence is a successful result when no candidate qualifies.
- **Thread batch**. One incremental inline publish from a judgment turn. Each batch is one GitHub review with an event of `COMMENT`.
- **Specialist tick**. A deterministic progress-comment edit after each specialist resolves. After publish, the specialist row shows accepted finding count for that specialist from the finding ledger (posted or resumed **inline review threads** plus **summary-only findings**). "No findings" means zero acceptances or an explicit empty / `no_findings` report.
- **Legacy review lens**. Historical `review-security`, `review-quality`, and `review-tests` values that remain readable in old comments, database rows, and fingerprints. New intake writes only `review`.
- **Agent session**. The provider-side conversation spanning multiple sends within one work item. Specialist sessions run in parallel; the review orchestrator owns the judging and summary session.
- **Trusted context**. Server-owned review facts and policy that remain outside untrusted evidence envelopes. It can guide investigation, but only the system prompt and server-owned tool/report contracts control agent authority.
- **Untrusted context**. PR-author, repository, reconnaissance, workspace, or external-tool content wrapped in a server-owned untrusted-evidence envelope. It may inform a finding but never supplies instructions or authority.
- **Pi session seam**. The pr-agent-owned interface (`createPiSession` / `PiSession`) that wraps the Pi coding-agent SDK. Feature harnesses create sessions only through this seam; raw Pi SDK construction and events stay inside `src/agent/runtime/`.
- **PR surface seam**. The pr-agent-owned interface (`createPrSurface` / `PrSurface`) that wraps GitHub REST I/O for a pull request. Feature harnesses and durable workers create surfaces only through this seam; `installationOctokit`, `@octokit/*`, and installation-token parameters stay inside `src/github/`. Leased durable workers pass mutations through the centralized epoch/cancellation boundary; `gitCredentialAuth()` is the only credential escape hatch for local git checkout.
- **Agent phase checkpoint**. Durable record of the last safely completed agent phase and its authoritative structured state for a work item and session role. Authoritative over resume snapshots for published progress.
- **Operation intent**. Idempotent, durable record of a planned GitHub mutation (stable operation key, with remote markers scoped to the work-item instance) persisted before the mutation with the owning lease epoch when leased, and reconciled into a publish record afterward. The boundary asserts the epoch immediately before the external call and before completion writes. Status distinguishes a provider-proven pre-acceptance rejection (`failed`, retryable) from an unknown outcome after the GitHub call may have landed (`outcome_unknown`, never auto-retried; resolve by publish-record or exact provider evidence, or surface it).
- **Resume snapshot**. Short-lived, tenant-scoped, encrypted blob of in-memory session state keyed by work item and session role. May resume computation from a recorded checkpoint; must not replay, advance, or roll back publish records.
- **Review phase**. A named stage used for metrics and retry attribution. Typed harness phases are `investigation`, `pre_submit`, `validation_repair`, `publish_recovery`, and `plaintext_fallback`. Orchestrated product stages include reconnaissance, specialist execution, judgment, thread publishing, and summary finalization.
- **Review queue**. pg-boss `agent-work-review` lane for orchestrated review runs, with worker concurrency `REVIEW_CONCURRENCY` (default `2`); one active review per pull request is enforced by the **PR actor lease**. Work is persisted in `agent_work_items` before the webhook returns.
- **Review superseding** — When a newer automated review is scheduled for the same pull request, older queued auto-review work for that PR is abandoned in favor of the latest head SHA. An in-flight auto-review may be cooperatively cancelled and replaced by one follow-up run for the newest head. A `synchronize` push triggers this from intake when `FEATURE_REVIEW=auto`: queued auto-reviews are superseded, the running one gets a cancel request observed by a fast poll while specialists run, and one deferred-head replacement is created (none when no auto review is active, so pushes never re-review a finished PR). Applies to automated `pull_request` events only, not slash-command reviews. A cancelled auto-review must not publish partial review output. The review progress comment may be edited once to note supersession (keeping the same CI + Recon + specialist table, with last-known phases) before the newer run’s intake replaces it with a fresh in-progress stub.
- **Review close cancel** — When a pull request is closed (`pull_request` `closed`), whether merged or not, any queued or running **Orchestrated review run** for that PR (auto or slash) is abandoned: queued work becomes `cancelled`, and running work gets a cooperative cancel request so the holder stops at its next checkpoint and releases the **PR actor lease**. The acknowledgement worker replaces the **review progress comment** with a short notice (`PR merged.` or `PR closed.`) and no progress table, and completes the **PR Agent Review** check run as `cancelled`. Slash `/review` remains available on a closed or merged PR and can enqueue a new run after prior review work is terminal.
- **Triage close cancel** — When a pull request is closed or merged, queued or running **Triage run** work becomes `cancelled`, with running Pi work stopping at its next checkpoint. The acknowledgement worker posts a terminal `-1` reaction and a clear no-push cancellation notice; duplicate close deliveries are deduped before cancellation SQL, and already-terminal rows are not changed.
- **Slash review deduplication**. If a command issuer invokes `/review` while an orchestrated review run is queued or in progress for that pull request, the bot acknowledges with a short reply on the command thread and does not enqueue duplicate work or alter the existing review progress comment.
- **Slash review cancel** — If a command issuer comments `/cancel` while an orchestrated review run is queued or in progress for that pull request, the bot immediately cancels that review (queued rows become cancelled; running rows get cooperative cancel), replaces the **review progress comment** with a short failure-style notice naming the issuer (`Cancelled by @login. Run \`/review\` to try again.`) with no progress table, and completes the **PR Agent Review** check run as `cancelled`. When no review is active, the bot replies that nothing is in progress.
- **Review stale-head reschedule** — If automatic-review preflight or a publish gate detects that the pull request head changed, the bot schedules one replacement run for the latest head. The replacement preserves the original source and slash-command context when present. If that replacement also goes stale, the run fails with retry guidance instead of rescheduling indefinitely.
- **Webhook parse error** — The JSON failed validation at the app boundary (unexpected or missing fields for that event type, or identifiers that cannot persist: non-integer or out-of-range PR/installation/comment/user ids, empty or oversized owner/repo/login/sha including `pull_request.before`); the delivery is not treated as processed for deduplication until parsing succeeds.
- **Review payload**. The structured, validated summary description emitted by the review orchestrator. It contains findings and overview gates and is consumed by the summary publisher.
- **Review progress comment**. The single `## PR Agent Review` conversation comment for an active or completed run. The acknowledgement worker creates a queued stub after durable intake (Head/Source, optional Queue wait rank, optional CI). When the review worker starts, the stub lists **Recon** plus the four specialists (specialists start as Waiting while recon runs). A recon-done tick flips specialists to Running. Specialist ticks edit that stub as reports resolve. The final summary replaces the last tick in place.
- **Review queue position**. Snapshot wait rank among queued review work items, shown on the queued **review progress comment** as a Queue table row (`#N of M`). Omitted once the run is in progress or when rank cannot be computed.
- **Review pointer body** — The top-level body of a pull request review on the Files Changed tab for one specialist batch: a NOTE linking to the **review progress comment** (`progress stub`) plus a specialist tagline. Does not host the agent fix prompt accordion.
- **Agent fix prompt** — Aggregate, copy-pasteable fix instructions for coding agents, combining all findings from an orchestrated review run and appending the **CI summary** plain-text digest (headline, failure reason/fixHint/url, permission note) inside a `<ci_summary untrusted="true">` block when that gate is rendered. Rendered as a “Fix all findings (agent prompt)” accordion on the **review summary comment**, below the findings table. Publish-time snapshot only; CI-refresh edits the CI table cell, not this accordion.
- **Finding fix prompt** — Per-finding copy-paste instructions inside an inline review thread’s “Prompt to fix” accordion; server-rendered (shared preamble and PR metadata, location header, then model-authored bug and fix direction). Distinct from the agent fix prompt aggregate on the review summary comment.
- **Suggestion patch** — Optional GitHub-native ` ```suggestion ` block attached to a finding’s inline review thread, offering a one-click applyable fix for human reviewers. Present only when the fix is mechanically expressible within the finding’s **commentable right line range**; findings needing cross-file or conceptual fixes carry only the **finding fix prompt**. Secondary to the fix prompts: the product is agent-first, human-visible second.
- **Review summary comment** — The completed form of a review progress comment: navigation and overview gates, not duplicated finding bodies from inline review threads. Owns "what's risky" (gates, findings table) and the aggregate **agent fix prompt** accordion below the table; never carries a per-file walkthrough or review map. When a published description agent block includes a **review map**, the summary links to that map instead of duplicating it; short omit-mode PRs get no link.
- **Review overview (`prCharacter`)** — Free-form Note on the review summary comment. Authored at synthesis via `publish_summary`. Uses the same **body scale** map as description writing policy (brief / standard / detailed from workspace size stats) plus ASD-STE100 short active sentences. States what the PR changes and review stakes; never inventories files, restates the findings table, or reports specialist-lane process.
- **Review size (`size`)** — T-shirt scale (`XS`, `S`, `M`, `L`, `XL`, `XXL`) for the magnitude of the change set, not code quality or review cost. Model-authored at synthesis. Shown as the Size row on the **review summary comment** and synced onto the PR as the managed `size:<TOKEN>` label when `FEATURE_REVIEW_LABELS` is on.
- **Finding confidence** — Per-finding certainty level (`c1`–`c5`) shown beside severity in the review summary comment; expresses how sure the reviewer is about one finding, nothing else. Prompts ask models to drop scored findings below the configured minimum (`REVIEW_MIN_CONFIDENCE`, default `1`).
- **CI summary** — Gate row on the **review progress comment** stub and completed **review summary comment**. Server fetches external check runs, legacy commit statuses, and (when failing) one condensed, redacted, size-bounded CI context for the PR head (Actions job logs, or check output if logs are unavailable; excluding PR Agent’s own check), then a small LLM turn authors structured fields (`headline`, per-failure `reason` / `fixHint`). Failing-head annotation and job-log fetches run concurrently within `REVIEW_CI_SUMMARY_FETCH_CONCURRENCY`; workflow runs are filtered to the reviewed head before any job listing, and raw job logs are bounded to a failure-preserving intake window before condensation. Server owns status facts, wait/poll, redaction, schema validation, and HTML rendering; the model must not emit the table markup. Ack uses a lightweight non-LLM snapshot only. When CI is still pending at publish, the row stays pending; a later `workflow_run` or `check_suite` completed webhook refreshes the CI cell on the matching summary without a full re-review. Missing Checks permission shows a grant-Checks row; missing Actions permission on a red head keeps the failure row and adds a grant-Actions note. Caps live in code constants (`REVIEW_CI_SUMMARY_*`). See [ADR 0018](docs/adr/0018-llm-authored-ci-summary.md).
- **Prose contract** — Changed Markdown that defines behavior (agent instructions, skill definitions, configuration docs) rather than merely describing it. The review orchestrator checks prose contracts for internal consistency: counts vs listed items, cross-references that resolve, command examples that are neither broken nor destructive, stated defaults vs the rest of the diff. Contradictions are ordinary findings, not style nits.
- **Truncated change set** — File listing for an orchestrated review run where some changed files are omitted due to configured caps; the run continues with explicit truncation metadata.
- **Ask run** — Execution of an agent work item that answers a command issuer's question about PR code; triggered by `/ask` or by an `@`-mention of the app bot on a pull request comment surface (PR conversation or inline review thread). Produces a plain-text **ask answer** (not a review payload or review summary comment). Explain-only: it does not change finding severity, dismiss findings, or mutate review summaries. Each run loads the containing comment thread (when GitHub exposes one) into the prompt as untrusted context so follow-ups read as a conversation; prior ask runs outside that thread are not joined.
- **Ask queue** — pg-boss `agent-work-ask` lane for ask runs, with worker concurrency `ASK_CONCURRENCY` (default `1`). Isolated from the review queue so review backlog cannot starve interactive Q&A.
- **Ask admission** — The transactional quota boundary shared by `/ask` and `@bot` mentions. It locks durable actor, repository, and installation token buckets, outstanding counts, and any installation provider reservation before inserting an ask work item. Throttled requests receive a bounded acknowledgement and no ask queue job.
- **Code anchor** — File path, line range, and diff hunk from an inline review comment; tells an ask run which code the command issuer was looking at.
- **Review failure notice** — A short PR conversation comment posted when an orchestrated review run reaches a terminal failed state after retries, telling maintainers the review did not complete and how to retry (for example `/review`). Uses neutral user-facing wording only; no attempt counts, tooling failures, or internal reasoning. Usually delivered by editing the existing review progress comment in place.
- **Summary-only finding** — A validated review finding that appears in the PR conversation summary because no stable inline review thread anchor exists on the cached PR diff. Not a failed review.
- **Commentable right line range** — A contiguous line range on the PR head (`RIGHT`) side that GitHub accepts for inline review comments, derived from the cached unified diff captured during `listPullRequestFiles`.
- **Public-output sanitizer** — Server-side guard that replaces credential- and assignment-shaped substrings in PR-visible **review** text before posting (substring `[redacted]`, not whole-field replacement). Overview internal failure phrasing is blocked separately by **Review payload** validation (reject → repair loop), not by the sanitizer.
- **Thread publish budget**. The maximum number of incremental `publish_thread` calls allowed per orchestrated review run (`MAX_THREAD_PUBLISH_CALLS`, default `8`). Findings accepted after exhaustion remain in the final summary as summary-only rows.
- **Ask failure reply** — Plain-text failure message posted at the ask reply target when an ask run fails permanently after retries. The terminal hook decides from durable state only: a completed `ask_reply` publish record or a recovered comment id. An `outcome_unknown` answer mutation is not delivery. If neither confirms an answer, exactly one failure reply goes through the `ask:failure_reply` operation-intent key.
- **Ask meta refusal** — A short ask answer posted without an LLM run when the question targets bot configuration, credentials, or internal instructions; distinct from an Ask run that investigates PR code.
- **Lightweight review completion** — An automated review work item that finishes without an **Orchestrated review run** because the change set qualified for a **Trivial change exemption**. Acknowledgement reaction and review progress comment intake still occur; the review progress comment is updated in place with a short public notice instead of a full review summary produced from a **Review payload**.
- **Trivial change exemption** — Policy allowing **Lightweight review completion** on automated pull request reviews when every changed file matches the docs-only allowlist and the change set is not a **Truncated change set**. Slash-command reviews are not exempted.
- **Review budget tier** — Advisory classification of pull request size (for example small, medium, or large) used to steer investigation focus. Does not by itself cancel an **Orchestrated review run**.
- **Finding fingerprint**. Stable identifier for a published finding, derived from the fixed `review` mode, location, and substance. Legacy lens candidates remain available so old findings are not reposted.
- **Stale review metadata**. Hidden machine-readable HTML in the review progress or summary comment recording the reviewed head SHA, the general `review` mode marker, and whether the head was stale when published.
- **Review run footer**. Muted provenance at the bottom of a completed review summary, including lightweight completion. It shows the short head SHA, the general review label, wall-clock duration, and model id. Wall-clock duration starts when the review worker starts the work item (not when the progress stub was posted while queued) and ends immediately before the final summary is rendered (after CI summary prep).
- **Dropped inline anchor** — An inline placement GitHub rejected for an invalid diff anchor; the finding remains in the **review summary comment** as a summary-only row (no separate maintainer note on the Files-tab review body).
- **Prior inline review feedback**. Context from earlier bot inline threads on the same pull request. Only a non-bot reply with a known user id and an association allowed by `MAINTAINER_DECISION_ASSOCIATIONS` enters authorized dismissal context; all other replies remain clearly labeled untrusted evidence, and reply text cannot grant authorization. A decision must match the finding location before it can support dismissal. `PrSurface.fetchPriorInlineFeedback` preserves the authorization metadata and takes the current review lens. Normalized `review` selects `review` plus recognized legacy lenses (`review-security`, `review-quality`, `review-tests`); an exact legacy lens selects only that lens. Pointer markers, legacy pointer strings, and triage/verification `publish_records` backfill still classify thread lenses.
- **Repo policy rules** — Maintainer-authored, version-controlled `.mdc` files under `.pr-agent/` that durably steer review behavior (optional `globs` / `alwaysApply` frontmatter plus markdown instructions). On an **Orchestrated review run**, matching rules bind only when the PR head and base repository identities match; fork, missing, or malformed identity renders PR-head rules as fenced untrusted evidence. The only cross-PR preference memory: the bot never learns silently from thread replies. After findings exist, publish prefilters each finding against bound same-repo rules that always apply or glob-match that finding's file, then one fail-closed judge call asks for the yes subset only (default no). An **inline review thread** lists a judged-yes relative path as a muted `Bound ·` subscript footer. Always-apply rules can appear on the threads that break them, not every thread. The specialist does not author a path. Fork, absent, invalid, empty policy, timeout, or an unasked path produces no footer, and the **review summary comment** never includes one.
- **Agent instruction files** — Well-known root Markdown files in the reviewed checkout (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`) that steer coding agents for that repository. On each **Orchestrated review run**, the worker statically loads any that exist at the PR head root into a context block parallel to **repo policy rules** (separate byte budgets; raw bodies; no `@include` expansion). Matching head/base repository identities produce binding trusted context; fork, missing, or malformed identity produces untrusted author text only. Binding violations matching the specialist reporting gate are ordinary findings.
- **Policy suggestion** — Bot-drafted repo policy guidance offered when a maintainer dismisses a finding, so the maintainer can commit the preference explicitly. When `.pr-agent/` has usable `.mdc` rules, verification suggests an append fragment if exactly one rule matches the finding path; otherwise it proposes a new `.mdc` starter. Triage always proposes a new `.mdc` starter without inspecting existing repo policy. The bot proposes the memory; a human review commits it.
- **Feature** — One of the eight user-facing `FEATURE_*` settings that decide what the bot does and when it spends tokens; the complete catalog lives in `docs/features.md`.
- **Capability mode** — The state of a feature: `off` (disabled entirely; slash commands reply with a disabled notice), `manual` (slash command only), or `auto` (slash command plus a fixed automatic trigger).
- **Token burner** — Any LLM-invoking surface other than the core orchestrated review run: description, ask, triage, and verification. Each is gated by its own feature so operators can stop its token spend outright.
- **Fingerprint suppression**. Skipping a new inline thread when its fingerprint or a recognized legacy candidate already belongs to the same pull request. The finding may still appear as a summary-only row.
- **Agent event** — Append-only metadata row for a span, LLM/tool lifecycle, decision, or publish step; never contains prompts or repo content. See [ADR 0024](docs/adr/0024-workspace-primary-grounding-and-evidence.md).
- **Evidence ledger** — Per work-item record of workspace reads (path, line range, content hash, head SHA) that may back a finding. See [ADR 0024](docs/adr/0024-workspace-primary-grounding-and-evidence.md).
- **Checkout coverage** — Explicit machine signal of how complete the local PR workspace is (`full` vs `sparse`) and whether search/read was truncated. See [ADR 0024](docs/adr/0024-workspace-primary-grounding-and-evidence.md).
- **Repo finding history** — Cross-PR fingerprint outcomes for a repository; suppression/threshold only; not preference memory. Durable prefs stay in `.pr-agent/*.mdc` ([ADR 0017](docs/adr/0017-mdc-repo-policy.md)). See [ADR 0024](docs/adr/0024-workspace-primary-grounding-and-evidence.md).
- **Ephemeral symbol index** — Per-run in-memory symbol map built from the checkout; discarded with the workspace. See [ADR 0024](docs/adr/0024-workspace-primary-grounding-and-evidence.md).
- **Code index hint** — Optional FTS (later vector) retrieval result used only as a navigation hint; never publishable without a following workspace read. See [ADR 0024](docs/adr/0024-workspace-primary-grounding-and-evidence.md).
