# Context glossary

This file is **domain language only** — not a specification of how the system is implemented.

- **Webhook delivery** — A single signed HTTP POST from GitHub to your app, identified by the `X-GitHub-Delivery` header (or deduplicated by raw body hash when that header is missing). Under the durable-queue design, every accepted delivery is recorded in durable storage before the HTTP response; duplicate deliveries are rejected by that record, not an in-memory map. A burst of deliveries must not be dropped at intake because workers are busy.
- **PR conversation** — The main pull request discussion timeline (GitHub models this as comments on an issue).
- **Inline review thread** — A thread anchored to a specific line/diff review comment on a pull request.
- **PR-surface I/O** — The set of GitHub REST calls the app makes around a pull request: acknowledgement reactions; creating or updating the review progress comment; posting or editing ask answers on the PR conversation or an inline review thread; fetching the PR head SHA; and publish-time review mutations (inline review threads, labels).
- **Slash command** — A **new** (`created`) comment whose first non-empty line begins with `/` followed by a command token.
- **Command issuer** — Anyone who can participate in the PR comment surface where the command appears.
- **Reply target** — Descriptor for where a slash command's response should appear (PR conversation vs inline review thread).
- **Draft pull request** — A PR still marked draft; this service runs the same automation on draft PRs as on ready PRs.
- **Acknowledgement reaction** — GitHub `eyes` / 👀 signaling that a webhook was accepted and work is in progress (on the PR issue and/or triggering comment). For automated pull request reviews, scheduled at durable webhook intake and published by a high-priority acknowledgement worker together with the review progress comment stub, before the orchestrated review run starts.
- **Agent work item** — A durable unit of background work created from a webhook delivery or slash command: a review, an ask, a description, a triage run, or a verification run. Tracks lifecycle (queued, running, superseded, cancelled, completed, failed) independently of the HTTP request that created it.
- **Description run** — Execution of an agent work item that generates a concise PR description (type, summary bullets, optional Mermaid diagram, file walkthrough) and publishes by merging into the pull request body. Triggered automatically on `pull_request` `opened` events and by `/describe`.
- **Description queue** — pg-boss `agent-work-description` lane with worker concurrency `DESCRIPTION_CONCURRENCY` (default `1`) and per-PR `key_strict_fifo` singleton keys.
- **Description agent block** — Generated markdown under `## PR Agent Description` in the PR body. Re-runs replace only this block; content above the header is treated as user-authored.
- **Triage run** — Slash-triggered work item for `/triage` that verifies prior PR Agent inline findings from the current specialist run and recognized legacy lens threads, fixes valid same-repo findings in a writable checkout, commits one fix per finding, pushes, then reports verdicts. PR-conversation `/triage` scopes to all eligible findings; inline-thread `/triage` scopes to one finding.
- **Triage verdict** — Per-finding outcome: `fixed`, `already-resolved`, `skipped`, or `dismissed`. Dismissed findings require maintainer reply evidence. **Triage run** never auto-resolves dismissed findings; **Verification run** acknowledges dismiss on its **verification stub** then resolves the thread. Shared vocabulary between **Triage run** and **Verification run**.
- **Verification run** — Automated, read-only agent work item enqueued on `pull_request` `synchronize` when `FEATURE_VERIFICATION=auto`. It re-checks each prior finding against the new head and emits a **triage verdict** per finding. Publish is quiet by default: **fixed** and **already-resolved** findings are resolved on the **inline review thread** with no new reply (if a prior **verification stub** exists, it is edited in place to a short fixed/already-resolved line so a stale still-open signal is not left behind); **skipped** (still open, and only when that finding's file changed in the push) updates one verification stub in place; **dismissed** edits that stub (evidence + **policy suggestion**) then resolves the thread. It never opens new findings, never edits code, and never uses a **writable PR checkout**. The worker short-circuits without an agent run when the PR has no unresolved open findings; rapid pushes collapse to the newest head under the same superseding rules as automated reviews. Distinct from an **Orchestrated review run** (which finds new issues) and a **Triage run** (which fixes them).
- **Verification stub** — The single bot reply on an **inline review thread** owned by **Verification run**, marked with `<!-- pr-agent:verification-stub -->`. Later verification publishes edit this comment instead of stacking new replies.
- **Triage report comment** — PR conversation comment under `## PR Agent Triage` with evaluated head SHA, pushed commits, verdict counts, and a per-finding table.
- **Writable PR checkout** — Fresh full clone for one triage run. It is never the shared PR repository view cache, never force-pushed, and only pushes fast-forward commits to the PR head branch.
- **Local PR workspace** — A temporary shallow checkout of the pull request head plus server-owned PR diff metadata, used by an **Orchestrated review run**, **Ask run**, **Description run**, or **Verification run** so the agent can inspect the full repository tree at the PR head without using GitHub read tools as its investigation surface.
- **PR repository view cache** — Worker-process ref-counted cache keyed by `owner/repo#pr:headSha` so concurrent jobs for the same PR commit share one git clone; released when the last job finishes.
- **Orchestrated review run**. The single review work item for a pull request. It performs reconnaissance, authors a specialist brief, runs four specialists, publishes incremental thread batches, and writes the final summary.
- **Review orchestrator**. The long-lived agent session that inspects the pull request, authors the specialist brief, judges reports, publishes thread batches, and synthesizes the summary.
- **Specialist**. One of four fixed investigator sessions: correctness, security, quality, or tests. Specialists run in parallel with a persona prompt and the specialist brief.
- **Specialist brief**. The structured handoff containing pull request intent, architecture notes, risk areas, a file map, and focus for each specialist.
- **Specialist report**. One specialist's structured submission. `no_findings` is an explicit successful empty report, not an error.
- **Thread batch**. One incremental inline publish from a judgment turn. Each batch is one GitHub review with an event of `COMMENT`.
- **Specialist tick**. A deterministic progress-comment edit after each specialist resolves.
- **Legacy review lens**. Historical `review-security`, `review-quality`, and `review-tests` values that remain readable in old comments, database rows, and fingerprints. New intake writes only `review`.
- **Agent session**. The provider-side conversation spanning multiple sends within one work item. Specialist sessions run in parallel; the review orchestrator owns the judging and summary session.
- **Review phase**. A named stage used for metrics and retry attribution. Orchestrated runs record reconnaissance, brief creation, specialist execution, judgment, thread publishing, and summary finalization.
- **Review queue**. pg-boss `agent-work-review` lane for orchestrated review runs, with worker concurrency `REVIEW_CONCURRENCY` (default `2`) and one active review slot per pull request. Work is persisted in `agent_work_items` before the webhook returns.
- **Review superseding** — When a newer automated review is scheduled for the same pull request, older queued auto-review work for that PR is abandoned in favor of the latest head SHA. An in-flight auto-review may be cooperatively cancelled and replaced by one follow-up run for the newest head. Applies to automated `pull_request` events only, not slash-command reviews. A cancelled auto-review must not publish partial review output. The review progress comment may be edited once to note supersession before the newer run’s intake replaces it with a fresh in-progress stub.
- **Slash review deduplication**. If a command issuer invokes `/review` while an orchestrated review run is queued or in progress for that pull request, the bot acknowledges with a short reply on the command thread and does not enqueue duplicate work or alter the existing review progress comment.
- **Slash review stale-head reschedule** — If a slash-command review reaches publish after the pull request head has changed, the bot may schedule one replacement run for the latest head while preserving the original command context. If that replacement also goes stale, the run fails with retry guidance instead of rescheduling indefinitely.
- **Webhook parse error** — The JSON failed validation at the app boundary (unexpected or missing fields for that event type); the delivery is not treated as processed for deduplication until parsing succeeds.
- **Review payload**. The structured, validated summary description emitted by the review orchestrator. It contains findings and overview gates and is consumed by the summary publisher.
- **Review progress comment**. The single `## PR Agent Review` conversation comment for an active or completed run. The acknowledgement worker creates a short stub after durable intake. Specialist ticks edit that stub as reports resolve. The final summary replaces the last tick in place.
- **Review pointer body** — The top-level body of a pull request review on the Files Changed tab; points readers to the review summary comment and may host the agent fix prompt accordion.
- **Review pointer link**. On later orchestrated runs, the review pointer body is only a markdown link to the single review summary comment. The first completed summary uses the plain pointer text.
- **Agent fix prompt** — Aggregate, copy-pasteable fix instructions for coding agents, combining all findings from an orchestrated review run.
- **Finding fix prompt** — Per-finding copy-paste instructions inside an inline review thread’s “Prompt to fix” accordion; server-rendered (shared preamble and PR metadata, location header, then model-authored bug and fix direction). Distinct from the agent fix prompt aggregate on the review pointer body.
- **Suggestion patch** — Optional GitHub-native ` ```suggestion ` block attached to a finding’s inline review thread, offering a one-click applyable fix for human reviewers. Present only when the fix is mechanically expressible within the finding’s **commentable right line range**; findings needing cross-file or conceptual fixes carry only the **finding fix prompt**. Secondary to the fix prompts: the product is agent-first, human-visible second.
- **Review summary comment** — The completed form of a review progress comment: navigation and overview gates, not duplicated finding bodies from inline review threads. Owns "what's risky" (merge verdict, gates, findings table); never carries a per-file walkthrough. When a description agent block exists on the PR, the summary links to its file walkthrough instead of duplicating it.
- **Finding confidence** — Per-finding certainty level (`c2`–`c5`) shown beside severity in the review summary comment; expresses how sure the reviewer is about one finding, nothing else.
- **Merge verdict** — Model-authored readiness assessment in the review summary comment: a score plus a one-sentence rationale written about the run's own findings. Consistency-clamped: open P1 findings cap the score and forbid safe-to-merge wording, enforced by review payload validation. All verdict and security wording is pass-scoped ("on this pass"), never an absolute safety promise. Distinct from **finding confidence**.
- **CI summary** — Gate row on the **review progress comment** stub and completed **review summary comment**. Server fetches external check runs, legacy commit statuses, and (when failing) condensed Actions job logs for the PR head (excluding PR Agent’s own check), then a small LLM turn authors structured fields (`headline`, per-failure `reason` / `fixHint`). Server owns status facts, wait/poll, redaction, schema validation, and HTML rendering; the model must not emit the table markup. Ack uses a lightweight non-LLM snapshot only. When CI is still pending at publish, the row stays pending; a later `workflow_run` completed webhook refreshes the CI cell on the matching summary without a full re-review. Missing Checks permission shows a grant-Checks row; missing Actions permission on a red head keeps the failure row and adds a grant-Actions note. Caps live in code constants (`REVIEW_CI_SUMMARY_*`). See [ADR 0026](docs/adr/0026-llm-authored-ci-summary.md).
- **Prose contract** — Changed Markdown that defines behavior (agent instructions, skill definitions, configuration docs) rather than merely describing it. The review orchestrator checks prose contracts for internal consistency: counts vs listed items, cross-references that resolve, command examples that are neither broken nor destructive, stated defaults vs the rest of the diff. Contradictions are ordinary findings, not style nits.
- **Truncated change set** — File listing for an orchestrated review run where some changed files are omitted due to configured caps; the run continues with explicit truncation metadata.
- **Ask run** — Execution of an agent work item that answers a command issuer's question about PR code; triggered by `/ask` or by an `@`-mention of the app bot on a pull request comment surface (PR conversation or inline review thread). Produces a plain-text **ask answer** (not a review payload or review summary comment). Explain-only: it does not change finding severity, dismiss findings, or mutate review summaries. Each run loads the containing comment thread (when GitHub exposes one) into the prompt as untrusted context so follow-ups read as a conversation; prior ask runs outside that thread are not joined.
- **Ask queue** — pg-boss `agent-work-ask` lane for ask runs, with worker concurrency `ASK_CONCURRENCY` (default `1`). Isolated from the review queue so review backlog cannot starve interactive Q&A.
- **Code anchor** — File path, line range, and diff hunk from an inline review comment; tells an ask run which code the command issuer was looking at.
- **Review failure notice** — A short PR conversation comment posted when an orchestrated review run reaches a terminal failed state after retries, telling maintainers the review did not complete and how to retry (for example `/review`). Uses neutral user-facing wording only; no attempt counts, tooling failures, or internal reasoning. Usually delivered by editing the existing review progress comment in place.
- **Summary-only finding** — A validated review finding that appears in the PR conversation summary because no stable inline review thread anchor exists on the cached PR diff. Not a failed review.
- **Commentable right line range** — A contiguous line range on the PR head (`RIGHT`) side that GitHub accepts for inline review comments, derived from the cached unified diff captured during `listPullRequestFiles`.
- **Public-output sanitizer** — Server-side guard that replaces credential- and assignment-shaped substrings in PR-visible **review** text before posting (substring `[redacted]`, not whole-field replacement). Overview internal failure phrasing is blocked separately by **Review payload** validation (reject → repair loop), not by the sanitizer.
- **Thread publish budget**. The maximum number of incremental `publish_thread` calls allowed per orchestrated review run (`MAX_THREAD_PUBLISH_CALLS`, default `8`). Findings accepted after exhaustion remain in the final summary as summary-only rows.
- **Ask failure reply** — Plain-text failure message posted at the ask reply target when an ask run fails permanently after retries.
- **Ask meta refusal** — A short ask answer posted without an LLM run when the question targets bot configuration, credentials, or internal instructions; distinct from an Ask run that investigates PR code.
- **Lightweight review completion** — An automated review work item that finishes without an **Orchestrated review run** because the change set qualified for a **Trivial change exemption**. Acknowledgement reaction and review progress comment intake still occur; the review progress comment is updated in place with a short public notice instead of a full review summary produced from a **Review payload**.
- **Trivial change exemption** — Policy allowing **Lightweight review completion** on automated pull request reviews when every changed file matches the docs-only allowlist and the change set is not a **Truncated change set**. Slash-command reviews are not exempted.
- **Review budget tier** — Advisory classification of pull request size (for example small, medium, or large) used to steer investigation focus. Does not by itself cancel an **Orchestrated review run**.
- **Finding fingerprint**. Stable identifier for a published finding, derived from the fixed `review` mode, location, and substance. Legacy lens candidates remain available so old findings are not reposted.
- **Stale review metadata**. Hidden machine-readable HTML in the review progress or summary comment recording the reviewed head SHA, the general `review` mode marker, and whether the head was stale when published.
- **Review run footer**. Muted provenance at the bottom of a completed review summary, including lightweight completion. It shows the short head SHA, the general review label, wall-clock duration, and model id.
- **Dropped inline anchor note** — Capped maintainer note on the **review pointer body** listing inline comments skipped because GitHub rejected their diff anchors; affected findings remain in the **review summary comment**.
- **Prior inline review feedback**. Trusted context from earlier bot inline threads on the same pull request where a maintainer replied. The orchestrator and specialists must weigh dismissals, such as false positive or intentional, before re-reporting. Legacy lens threads are included.
- **Repo policy rules** — Maintainer-authored, version-controlled `.mdc` files under `.pr-agent/` that durably steer review behavior (optional `globs` / `alwaysApply` frontmatter plus markdown instructions). The only cross-PR preference memory: the bot never learns silently from thread replies.
- **Agent instruction files** — Well-known root Markdown files in the reviewed checkout (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`) that steer coding agents for that repository. On each **Orchestrated review run**, the worker statically loads any that exist at the PR head root into a trusted-context block parallel to **repo policy rules** (separate byte budgets; raw bodies; no `@include` expansion). When present they are binding for that review: evidenced violations matching the specialist reporting gate are ordinary findings.
- **Policy suggestion** — Bot-drafted repo policy guidance offered when a maintainer dismisses a finding, so the maintainer can commit the preference explicitly. When `.pr-agent/` has usable `.mdc` rules, verification suggests an append fragment if exactly one rule matches the finding path; otherwise it proposes a new `.mdc` starter. Triage always proposes a new `.mdc` starter (no checkout). The bot proposes the memory; a human review commits it.
- **Feature** — One of the eight user-facing `FEATURE_*` settings that decide what the bot does and when it spends tokens; the complete catalog lives in `docs/features.md`.
- **Capability mode** — The state of a feature: `off` (disabled entirely; slash commands reply with a disabled notice), `manual` (slash command only), or `auto` (slash command plus a fixed automatic trigger).
- **Token burner** — Any LLM-invoking surface other than the core orchestrated review run: description, ask, triage, and verification. Each is gated by its own feature so operators can stop its token spend outright.
- **Fingerprint suppression**. Skipping a new inline thread when its fingerprint or a recognized legacy candidate already belongs to the same pull request. The finding may still appear as a summary-only row.
